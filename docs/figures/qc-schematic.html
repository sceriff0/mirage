Supplementary Figure S3 · quality control

Quality control as one seam: a tagged artifact stream, a step-owned kind vocabulary, three guards, and a failure contract that stops the run

S1 · pipeline S2 · registration S3 · quality control S4 · lazy reads S5 · coarse alignment S6 · accuracy measures

Every step of the pipeline emits quality-control artifacts, and every one of them reaches the end-of-run report through the same one-channel interface: a stream of [kind, file] pairs. What a kind is has a single owner — the same step table that defines --start and --stop — and three separate guards make a mistyped or unwired kind a hard error rather than a silently empty section of a green report. Every QC gate below is on by default, and every QC process is gating: it retries a signal kill up to three times and then fails the run. That is the reverse of what this figure said before 2026-08-25, and the reversal is the point — the old 'ignore' fallback let a broken QC step exit 0 with an incomplete tree. Two opt-in evaluators are the only survivors of the old policy, and when either drops, the run log says so.

b

The interface — one stream of [kind, file], and three guards on it

Artifacts arrive as one channel of tagged pairs, not as eight positional channels. A caller mixes in what it has; a kind nobody contributes is an empty branch. That removes the Channel.empty().collect().ifEmpty([]) placeholders both callers used to repeat — but it also removes the compiler's help, because a mistyped tag is now a runtime string rather than a parse-time resolution failure. Three guards put that safety back.

FINAL_QC( ch_artifacts, ch_run_facts )
  ch_artifacts : Channel<[String kind, Path file]>
ParamUtils.knownArtifactKinds()
  = STEPS.collectMany { it.qcKinds }
  + UNIVERSAL_QC_KINDS
  → 8 kinds, a fresh List every call; see panel c for the split
The vocabulary is derived, not restated. The two FINAL_QC call sites hand-write 25 ['kind', file] tag literals between them, counted on one basis — every literal in each site's channel-mix chain, unconditional pair included: 18 on the standard path (the unconditional INPUT_CHECK pair, plus 16 across four if blocks, in which versions and size_log each appear five times) and 7 in add_cycle (versions×2, size_log×2, plus one each of registration_qc, seg_qc, seg_residuals — 5 distinct kinds, not 7 literals) — and nothing else checks that the two agree. ParamUtils.knownArtifactKinds() is that check, and it is computed from the same step table that fixes each step's required samplesheet columns and the values --start/--stop accept. It is a pure static accessor rather than file-level state on purpose — Nextflow 26's strict parser rejects a bare top-level KNOWN_ARTIFACT_KINDS = ... assignment in a subworkflow file outright.
1 · unknown tag at the producer
subscribe on ch_artifacts
A tag not in the vocabulary is a hard error. Registered unconditionally — outside both parameter gates — so a typo is caught even on a run that asks for neither output. Without it an unknown tag would match no filter and that whole QC category would vanish from the report while the run stayed green.
2 · unknown literal at the consumer
artifactsOf(ch, kind)
The eight artifactsOf() calls are a second, textually separate copy of the vocabulary. The helper validates its own kind argument, so artifactsOf(ch, 'seg_qcc') throws instead of quietly emptying a report slot.
3 · declared but never consumed
consumed_kinds — 3rd arg to artifactsOf()
The third failure the first two cannot see: a kind correctly declared, correctly tagged, and read by no artifactsOf() call — dropped from every report, exit 0. consumed_kinds is a local Set declared in main:, not file-level state (a static mutable Set in lib/ would be shared across every run in the JVM), so it is threaded as a mandatory third argument into all eight artifactsOf() call sites and checked against the full vocabulary at the end of the workflow, and only when both outputs are enabled, because setting skip_final_qc_report — with the final report skipped — or setting enable_trace off, via a profile or -params-file, legitimately leaves half the vocabulary unconsumed.

The container cell above names the readable tag, not what actually runs. cdgatenbee/valis-wsi:1.0.0 is the third-party base image; at runtime lib/WarpBackends.groovy and modules/local/register.nf both pin it to a digest of that same build (@sha256:eac27cc5…, resolved 2026-09-02) rather than the mutable tag — a supply-chain hardening (R6). This cell keeps the human-readable tag because a bare digest is unreadable in a supplement. bolt3x/mirage-tiled:1.0.0, and every bolt3x/mirage-* image named elsewhere in this figure, are the pipeline's own published, content-descriptive tags and are not digest-pinned — R6 pins only the externally-sourced base image.

The per-cell residual CSV is never published. WARP_SEG_QC's publishDir carries pattern: "*_seg_qc.json" and replaces the process-level default, so *_reg_residuals.csv — an optional output: emit — reaches --outdir through no path at all. It travels as the seg_residuals kind into the report's data bundle (panel f, slot 8) and is separately joined onto the cell mask by the SpatialData export. The published QC tree under <pid>/qc/registration/ therefore holds the metrics JSON, the tiled backend's *_tre.json, and nothing else at that level.

The JVM-only --jvm-heap-gb 8 lives in the backend table rather than in ext.args, and that is the point: an ext.args ternary keyed on params.registration_method would read the global param while the process selects its backend from an input. Resolving it from the table — which already closes over method — makes leaking a VALIS flag onto the JVM-free path structurally impossible instead of conditionally absent. One 8-element input tuple serves both backends; only the two joins upstream differ.

A third artifact lands in <outdir>/qc/ and is not in the stream at all. mirage_resource_report.html is written by a workflow.onComplete handler in main.nf, not by a process, because trace.txt is only finalised at workflow completion and an in-DAG process could not read it. It is best-effort in the strongest sense: any failure — no python3 on the head node, no trace file — logs a warning and never fails the run. It is gated by enable_trace, the same parameter as the size-log rollup.
both are declared cache = false, and that is correct Their inputs come from collectFile(), which is an operator, not a task: it re-executes every run and writes to a fresh work/tmp/<hash>/, so under Nextflow's default hashing the input is a new file each time and the task could never cache. run_summary.json additionally embeds a wall-clock timestamp, so its content legitimately differs every run. Declaring it changes no behaviour — but it is what makes the resume guard assertable: on a fully cached -resume, these two and only these two re-run.
Every list slot is collect(sort: true), never a bare collect(). Process path collections are hashed positionally and collect() emits in arrival order, so identical reruns produced different task hashes. collated_versions.yml carries sort: true for the same reason one level down, at the level of file content.
g

The failure contract — retry, then fail the run

Every consumer of QC output is a collect() / collectFile() / combine() / join() — none of which requires a fixed item count, so a missing QC artifact cannot deadlock the DAG. That is a property of the wiring, and it is what once made an 'ignore' fallback look free. It was not free, and it is gone: one withName: selector now states retry-then-fail for all seven QC processes at once.

GENERATE_PREPROCESS_QCGENERATE_REGISTRATION_QCGENERATE_POSTPROCESSING_QC GENERATE_QC_REPORTSEG_QC_SEGMENTSEG_QC_GEOJSONWARP_SEG_QC
errorStrategy = { task.exitStatus in ((130..145) + 104) && task.attempt <= 3 ? 'retry' : 'finish' }   maxRetries = 3, pinned here
Why the whole 130–145 range. That is the entire "killed by a signal" band, not a hand-picked subset. The kill actually observed on WARP_SEG_QC was 140 = 128 + 12 = SIGUSR2 — SLURM's pre-walltime warning, not the SIGTERM an older comment claimed. With an enumerated subset, anything outside it was ignored on attempt 1 and threw away the entire retry budget. The pipeline-wide default retries only 104/134/135/137/139/140/143; this block differs from it in the width of the retry range, not in where it ends up — both finish the run once the budget is spent.
Why maxRetries is pinned here rather than inherited. A dynamic strategy that returns 'retry' after the budget is exhausted is treated as fatal — precisely what this block exists to avoid. Pinning keeps the closure's cutoff in lockstep with the budget on every profile.
this contract was reversed on 2026-08-25 The fallback used to be 'ignore': a QC task that exhausted its budget was dropped and the run still exited 0, so an empty report section looked identical whether its producer had been ignored or the step had never run. Forcing WARP_SEG_QC to exit 1 gave shell exit 0, a full-looking tree, and zero *_seg_qc.json. The fallback is now 'finish' — in-flight tasks drain, every failure is reported at once, and the run fails. On the default path a green run now does imply a complete QC tree.
Two opt-in evaluators keep the old policy, deliberately. SEG_QUALITY_EVAL and MERGE_SEG_EVAL — reference-free segmentation scoring, off unless the seg_quality profile is passed — carry { task.attempt <= 3 ? 'retry' : 'ignore' }, because losing a QualityScore degrades QC and nothing else. The drop is announced, not inferred: main.nf's onComplete reads workflow.stats.ignoredCount and warns that the run is reported successful with an incomplete tree.
The guards in panel b are the other half of the same problem. The errorStrategy now makes a failed QC task loud; the three vocabulary guards make a miswired one loud too. Both silences were once reachable, and only one of them was ever a policy.

Supplementary Figure S3. The quality-control architecture. (a) Each of the four ordered steps contributes QC behind its own parameter gate, all of them open at the shipped defaults; segmentation contributes no step-specific kind, and every process in the pipeline contributes the two universal ones. (b) All of it reaches the end-of-run aggregation through a single channel of [kind, file] pairs rather than eight positional channels — an interface that costs nothing for an absent kind but replaces a parse-time resolution failure with a runtime string, so three guards restore the lost safety: an unknown tag at the producer, an unknown filter literal at the consumer, and a declared kind that no consumer reads. (c) The kind vocabulary is derived from ParamUtils.STEPS, the same table that fixes step order, required samplesheet columns and entry columns, plus a separate list of the cross-cutting kinds every step emits. (d) Three per-step renderers produce the QC images, each pinned to a container and published under the patient's qc/ tree; the registration renderer draws a two-panel before/after composite from all three of its staged inputs, built by pad-or-crop rather than rescale so the "before" panel cannot understate the pre-registration error. (e) At reg_qc = 2 a shared subworkflow segments each slide on its native image with the run's own segmenter — an alias of SEGMENT, so the QC cannot drift from what the run ships — traces the mask to polygons, and warps those polygons through every registration stage in one process that serves both registration backends from a table keyed on the method argument. (f) Aggregation is eight fixed, sorted input slots plus a size-log rollup, both uncacheable by construction; the report itself renders per-stage error-distribution plots and a log-log feature-TRE-vs-cell-displacement scatter rather than per-slide tables, hand-rolled as stdlib-only inline SVG so it stays runnable inside the preprocess container that publishes it. (g) All seven QC processes retry the whole signal range and then finish: a broken QC step fails the run, so on the default path a green run does imply a complete QC tree. Only the two opt-in evaluators (SEG_QUALITY_EVAL, MERGE_SEG_EVAL) still fall back to ignore, and a drop is announced through workflow.stats.ignoredCount rather than left to be inferred. (h) QC defaults. Supplementary Figure S1 places these processes in the whole workflow; Supplementary Figure S2 takes the reg_qc ladder apart per registration backend. Process names, containers, resource requests, published paths, parameter defaults and the artifact vocabulary are read verbatim from the pipeline source (subworkflows/local/final_qc.nf, subworkflows/local/seg_qc.nf, lib/ParamUtils.groovy, lib/WarpBackends.groovy, modules/local/generate_{preprocess,registration,postprocessing}_qc.nf, modules/local/generate_qc_report.nf, modules/local/aggregate_size_logs.nf, modules/local/{seg_qc_geojson,warp_seg_qc}.nf, conf/modules.config, conf/base.config, nextflow.config).
