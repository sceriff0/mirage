Supplementary Figure S5 · coarse alignment

STARE's coarse anchor: a learned DISK + LightGlue matcher estimates one global pose per moving slide, and its residual — not its speed — is what the per-tile step depends on

S1 · pipeline S2 · registration S3 · quality control S4 · lazy reads S5 · coarse alignment S6 · accuracy measures

The STARE (tiled) registration backend's first step — TILED_COARSE — estimates a single whole-slide affine M0 on a downsampled thumbnail before the per-tile step refines the small residual left over. For v1.0.0 the front-end that produces that estimate changed from three classical, non-learned feature matchers to one learned matcher, DISK + LightGlue, run CPU-only inside the same task. This figure grounds why that swap happened, what the code kept unchanged underneath it, why the memory curve now has a different shape, and what is — and is not — verified about the replacement.

a

The naive expectation — a cheap thumbnail step, any detector would do

Coarse alignment looks like it only has to be fast: a whole-slide anchor computed on a small thumbnail, refined later. What it actually has to deliver is a residual narrow enough to land inside the window the per-tile step reads — that requirement, not runtime, is what selects the matcher.

COARSE delivers
M0 + residual (px)
One 3×3 affine mapping moving → reference pixels, plus a residual TRE — estimate_rigid's return value.
the constraint
residual < halo
The per-tile step reads a tile core expanded by reg_tiled_halo px and clamped to the image — the capture radius the anchor's residual must land inside. Default 256 px (STARE has one default configuration; the cost tiers were removed).
what enforces it
nothing
TILED_COARSE logs a warning once the residual reaches the halo, but nothing downstream checks it and no task fails on it — a slide can mis-register silently and the run still exits 0.
Why this is a correctness requirement, not a speed one. A faster, worse matcher does not merely take a different amount of time — it produces a wider residual, and once that residual reaches the halo the per-tile step is measuring a shift to the wrong structure while the pipeline keeps running. The matcher is chosen for what it can find inside that budget, not for how quickly it runs.
b

Why the front-end changed, and what did not

Three non-learned, classical feature-matching front-ends preceded this one, plus a selector parameter choosing among all four. All four were deleted outright for v1.0.0 — not kept behind a flag — because a dispatch table with one live value is dead config and the deleted three were not the method being replicated. The numerically load-bearing fit underneath every one of them was never touched.

changed — the front-end
the matcherdeleted & replaced
What produces point correspondences between the two thumbnails. The module's own docstring now reads "Learned feature matching (DISK + LightGlue) handles the inter-cycle rotation/translation" — it used to name a different, classical technique in the same sentence.
unchanged — the fit
estimate_transform_from_matchesuntouched
RANSAC + model fit over whatever correspondences the front-end hands it, plus scale_transform_to_full_res, the thumbnail-to-full-resolution lift. Same function, same signature, before and after the swap.
Why cross-cycle thumbnails are hard to match, regardless of matcher. Reference and moving planes come from different imaging cycles with different exposures: two views of the same tissue can arrive at wildly different dynamic ranges and match each other far worse than they should, with no error raised. That is a correspondence problem — what a matcher can find in the two images — never a geometry problem in how the fit is solved from what it finds. The front-end swap targets exactly the half of the step that owns correspondences; it could not have targeted the other half, because the other half was never where the difficulty was.
c

The mechanism — from two raw planes to one lifted transform

Six steps, run once per moving slide. The tensor shapes are the part the code makes hardest to hold in one pass, so they are spelled out at every stage.

1normalize_intensity
Raw decimated plane, H×W float32 counts (0–65535) → rescaled to [0, 1] over a p1–p99.9 percentile window (_NORM_PCT) — the range DISK was trained on, and a correctness fix for the cross-cycle exposure mismatch in panel b, not only a domain-range one.
2reshape for DISK
Normalised plane → a 1×3×H×W float32 tensor, the single channel repeated across three (_to_disk_tensor). Reference and moving are each converted independently.
3DISK.from_pretrained("depth")
Two forward passes, one per plane. Internally padded to a multiple of 16 (pad_if_not_divisible=True — its U-Net downsamples by 16 and raises on a thumbnail whose dimensions are not multiples of it), up to 2048 keypoints per plane (n_keypoints, the module default — bin/tiled_coarse.py never overrides it). Each call returns keypoints (N×2) and descriptors, on CPU only.
4LightGlue("disk")
Both keypoint/descriptor sets in → an M×2 match-index array out, column 0 indexing the reference set and column 1 the moving set.
5RANSAC euclidean fit
estimate_transform_from_matches(src, dst) — default model euclidean (rotation + translation, 3 DOF), 1000 trials, 3 px inlier threshold → a 3×3 matrix M0 in thumbnail pixels, plus (residual_px, n_inliers).
6lift to full resolution
scale_transform_to_full_res multiplies the translation column by the decimation factor (rotation is scale-invariant and passes through unchanged); the residual is scaled by the same factor. Both COARSE outputs — M0 and the reported coarse_tre — are full-resolution numbers from this point on.
d

The memory shape — a U-Net's activations, not a corner detector's

DISK is a U-Net: its activation memory scales with thumbnail area, not with keypoint count or with the slide's own dimensions. That single fact reshaped a resource request and moved a tier column.

activation memory, per call
DISK forward passscales with area
GB ≈ 1.1 + 7.3 × Mpx — measured on the pinned stack (3.03 GB at 512 px, 8.78 GB at 1024 px thumbnails). At the shipped high tier (2048 px → 4.19 Mpx) that is ≈31.7 GB; TILED_COARSE's memory closure applies 1.5× headroom on top to reach the 48 GB it actually requests.
model weights, cached once
_DISK_MODELSbuilt once per process
A module-level dict keyed on device, holding both DISK and LightGlue after the first call — because building both models dominates a single call, not because repeat inference is slow. It matters for the in-process oracle and the test suite; a fresh TILED_COARSE task pays that cost exactly once.
Why reg_tiled_coarse_max_dim is now a memory knob, not just a time knob. Raising the thumbnail bound is no longer a free accuracy trade: the shipped high tier is 2048 px, not the 4096 an earlier iteration shipped — the whole tier column moved down one step for v1.0.0 because of this same area-scaling formula. A 256 px floor is enforced at launch, before any task starts: below it, the decimator treats the bound as "no decimation" and would hand DISK the full-resolution plane — a guaranteed OOM now that the matcher is a U-Net rather than a cheap corner detector.
e

The knobs

Defaults verbatim from the params{} block of nextflow.config, the only place a default is declared. reg_tiled_coarse_max_dim and reg_tiled_halo carry plain defaults and are set directly (the reg_tiled_mode cost tiers were removed; passing it is refused at launch unless it is high).

reg_tiled_coarse_max_dim1024 M0 thumbnail longest side (px) — the knob from panel d. 256 px floor enforced at launch.
reg_tiled_halo256 tile read halo = the capture radius from panel a (px).
f

Honest limits

Three things this front-end swap does not have behind it, stated plainly rather than left for a reviewer to discover.

1 — no head-to-head measurement No accuracy comparison between the three deleted classical front-ends and the learned one is recorded anywhere in this tree. The change's own record states a methodological reason — the classical alternatives were not the front-end being replicated — not a measured one. The only tests exercising the learned front-end directly recover a pure synthetic pixel shift injected into a random blob image; there is no real-slide accuracy test for it, classical or learned.
2 — no CPU fallback If torch or the learned matcher's library fail to import, the front-end raises a RuntimeError naming the missing dependency and the pinned versions to install — there is no classical detector left to fall back to. A deployment node missing the pinned stack fails the task outright rather than degrading.
3 — the residual is an estimate, not a per-pixel guarantee Both M0 and its residual are computed on the thumbnail and then lifted to full resolution by a single multiplicative scale — they are never re-measured at full resolution. The reported residual is therefore an estimate of the global pose error, not a guarantee about any individual full-resolution pixel.

Supplementary Figure S5. The STARE coarse front-end. (a) TILED_COARSE estimates one global affine per moving slide on a shared thumbnail; the per-tile step that follows can only recover a residual that lands inside its read halo, and nothing downstream checks that it did — a wide residual mis-registers a slide while the run still exits 0. (b) Three earlier, classical feature-matching front-ends and their selector parameter were deleted outright and replaced by a single learned matcher (DISK + LightGlue) for v1.0.0; the RANSAC fit and the thumbnail-to-full-resolution lift underneath every front-end, past and present, were never touched — what changed was only how correspondences are found between two cross-cycle thumbnails. (c) Six steps carry a plane from raw counts to a lifted transform: percentile normalisation, a batched tensor reshape, two DISK forward passes (padded internally to a multiple of 16, up to 2048 keypoints each, CPU-only), a LightGlue match, a RANSAC euclidean fit, and a full-resolution lift. (d) Because the matcher is a U-Net, its activation memory scales with thumbnail area (GB ≈ 1.1 + 7.3 × Mpx) rather than staying near-flat the way a classical corner detector's did — the resource request this step asks for, and the tier this pipeline ships at, both moved to respect that curve. (e) The two knobs governing this step's cost and accuracy carry plain defaults in nextflow.config and are set directly (the cost tiers were removed). (f) The replacement is unmeasured head-to-head against what it replaced, has no fallback if its learned stack is unavailable, and reports a residual that is an estimate lifted from a thumbnail, not a full-resolution guarantee.
