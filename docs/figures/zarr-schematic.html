Supplementary Figure S4 · lazy reads

A peak-memory transition, not an I/O one: where a lazy zarr view turns O(channels) into O(1), where the pipeline genuinely needs every pixel, and three audit claims that reading the read sites got wrong

S1 · pipeline S2 · registration S3 · quality control S4 · lazy reads S5 · coarse alignment S6 · accuracy measures

Lazy, region-readable zarr views of an OME-TIFF were never missing from this pipeline: bin/utils/tiled_io.py has carried open_lazy, read_decimated and decimation_factor since the STARE tiled backend was built, and three tiled scripts were their only consumers. What changed is the blast radius — five further sites now read one channel, one plane or one band where they used to read the whole stack, and a sixth eager read, owned by a different library, was later taken through that library's own lazy API. The gain is peak memory, not bytes read: at four of the five, the number of source pixels decoded is unchanged, because a published full-resolution artifact, an anti-aliased resize, or a whole-image statistic still demands every one of them. Each claim below is stated at the confidence it earned; every process where laziness buys nothing is named with the reason; and three places where the audit that scoped this work was wrong are recorded, because the reason they were wrong generalises.

a

What the pipeline already had, and what a reader assumes it gained

The natural reading of "the pipeline now uses zarr" is that it reads fewer bytes off disk. At four of the five sites it does not. Two independent axes of overread exist, and only one of them was ever available to remove.

THE CHANNEL AXIS — removable

C planes decoded to use 1

A slide is (C, H, W). tifffile.imread decodes every marker channel; the consumer then indexes one out of it. A zarr view indexes first and decodes only the tiles that slice touches. This is the axis all four changed sites moved on.

open_lazy — bin/utils/tiled_io.py:34

THE SPATIAL AXIS — not removable here

full resolution decoded to emit a thumbnail

Reading [::f, ::f] instead of the full plane would be the larger win — and it is available at none of the five sites. The conclusion is uniform; the mechanism is not, and this box used to claim it was. Only site 1 reaches it through decimation_factor(..., max_dim=None) → 1. Site 2 hard-codes read_decimated(..., factor=1) and never calls the resolver. Sites 3, 4 and 5 (SPLIT_CHANNELS, SEGMENT, MERGE_AND_PYRAMID) slice regions off the lazy view directly and call neither — they have no decimation path to disable. Panels f and g give the three separate reasons the win is unavailable in each case.

bin/utils/qc.py:571 (the one decimation_factor call) · bin/generate_preprocess_qc.py:211 (factor=1, hard-coded) · decimation_factor — bin/utils/tiled_io.py:88 (returns 1 when max_dim is None)
the capability was never missing — only its reach open_lazy / read_decimated / decimation_factor predate this work and were consumed by exactly three scripts — tiled_coarse.py (through bin/utils/coarse_align.py), tiled_reg_tile.py and tiled_stitch.py, all on the STARE tiled registration path. Everything else in bin/ read eagerly. No dependency was added either: every affected container already pinned zarr==2.18.3 (containers/preprocess, regqc, stardist, cellsam, tiled).
b

The primitive: one lazy view, one banded reader, one decimation rule

Three functions in one file, unchanged by this work. Every new call site goes through them rather than opening its own zarr store, so the (C, H, W) contract and the banding behaviour keep a single owner.

# bin/utils/tiled_io.py open_lazy(path) -> (arr, dtype, close) tifffile.imread(..., aszarr=True) + zarr.open; base level if pyramidal; 2-D promoted to C=1; arr[c, y0:y1, x0:x1] decimation_factor(shapes, max_dim) -> int ONE shared factor for every shape; 1 when max_dim is None read_decimated(src, index, factor, band_bytes=DEFAULT_BAND_BYTES) -> float32 plane, streamed in row bands, strided [::f, ::f] per band DEFAULT_BAND_BYTES = 64 * 1024 * 1024 # a BYTE budget, not a row count

the (C,H,W) contract

open_lazy presents channel-first only. It has no notion of a (Y, X, C) layout, which is why every new call site keeps an eager fallback for that case — see panel g, blocker 4.

bin/utils/tiled_io.py:68-85

why bytes, not rows

A fixed row count is not a memory bound: a band of a 30k-wide slide is ~7× the same band of a 4k-wide one. band_rows_for divides the budget by the row width, then snaps down to a multiple of factor so the sampled rows stay globally aligned.

bin/utils/tiled_io.py:113-125

one factor, not one per slide

The shared factor is a correctness requirement of the STARE coarse anchor, not a convenience: squeezing each slide under max_dim independently would introduce a scale change between the two thumbnails and bake a bogus scale term into M0.

bin/utils/tiled_io.py:88-99

The evidence, and how each number was obtained

Three measurements exist. The first supports the headline; the second falsified a comment; the third belongs to the BioIO convert of panel g and is the only one taken against a real production function. All were taken on one laptop, on synthetic data, outside the production containers, with harnesses that were scratch files — so not one of the megabyte figures is reproducible from the repository. What is reproducible, and only for the third, is the mechanism: its decode-count property is pinned by a committed test.

GENERATE_PREPROCESS_QC, maximum resident set size. The percentages (9.2% and 29.9%) are the least interesting numbers here — both runs carry a shared ~650–750 MB interpreter/NumPy/scikit-image/zarr import floor that dilutes them. The shape is the result: doubling the channel count grew the old peak by +259.5 MB (+31%) and the new peak by +10 MB (+1.3%) — O(channels) becoming O(1).

HOW — the RSS measurement

/usr/bin/time -l on macOS (OS-level maximum RSS, not Python-tracked allocations), synthetic uint16 (C, 4000, 4000) OME-TIFFs at 250 MB per channel, each run in a fresh subprocess, comparing a same-process reimplementation of the old loop against the real patched function. A separate tracemalloc run on the 8-channel case gave 536.2 MB against 351.6 MB — the same direction, by a different instrument.

recorded in the task-2 implementation report; harness not committed

HOW — the memmap probe

A 6-channel 2000×2000 uint16 OME-TIFF (48.0 MB on disk; one plane = 8.0 MB). The old path's returned array spans 48.0 MB — all six channels, though only channel 0 is ever read; the new path materialises 8.0 MB. The returned numpy.memmap's backing file was inspected directly and is a tmp*.memmap, not the source .tif.

recorded in the task-4 implementation report; probe not committed
what these numbers are not No measurement ran inside the production container, on a gigapixel slide, or with a full marker panel. The scaling argument is structural and does not depend on any of that; the specific percentages do, and must not be quoted as production figures.

HOW — the BioIO convert, the third measurement

A 144 MB 8 × 3000 × 3000 uint16 OME-TIFF, opened as a lazy dask array over a tifffile zarr store — the same shape of object BioImage.dask_data is — and written through the real ome_io.write_ome_tiff. Peak is resource.getrusage(RUSAGE_SELF).ru_maxrss, sampled in a fresh subprocess per variant (not tracemalloc, which does not see NumPy's allocations); all outputs byte-identical with the OME UUID masked.

e

The trap this replaced: asarray(out="memmap") does not map the source

Both segmentation backends carried a comment saying they used memory-mapped I/O "to avoid loading the entire multichannel image". On compressed input the call does the opposite, and does it to scratch disk as well as to RAM. Those comments now describe what the code does.

Verified directly on the 6-channel probe of panel d. The same out="memmap" pattern survives at bin/utils/image_utils.py:210, behind load_image(..., memmap=True), and was deliberately left alone: no caller in bin/ ever passes memmap=True, so it is reported dead code rather than a fixed site.

g

Four structural blockers, and the one opportunity that was left — now taken

Beyond the fourteen processes of panel f, four specific mechanisms make a spatial saving unavailable even at sites that are now lazy. They are why factor is 1 everywhere outside STARE.

1 — anti-aliased downsampling needs every source pixel

downsample_image calls skimage.transform.resize(order=1, anti_aliasing=True). read_decimated does [::f, ::f] — naive subsampling. Substituting one for the other changes the published image and injects aliasing. So at a downsampling site no I/O saving is available, ever: the place the win looks largest is exactly the place it is forbidden.

bin/generate_preprocess_qc.py:98-126

2 — the full-resolution read feeds a published artifact

Registration QC's *_QC_RGB_fullres.tif is published under <patient>/qc/registration/. A --no-fullres flag exists in the CLI, but the process' config block passes no ext.args, so it is never used in production. Decimating this read would silently degrade a deliverable rather than save anything.

bin/generate_registration_qc.py:175 · conf/modules.config, GENERATE_REGISTRATION_QC publishDir

3 — a cross-plane comparison in a samples-last layout

read_single_ndpi tests image_data[...,0] == [...,1] == [...,2] to decide whether an NDPI's RGB is really greyscale. That is samples-last and needs all three planes at once — incompatible with tiled_io's channel-first (C, H, W) contract.

bin/convert_image.py:161-175

4 — the (Y, X, C) fallback, kept and never exercised

Two of the five changed sites keep the old eager whole-stack path for a channel-last on-disk layout, because open_lazy is channel-first only. This pipeline's own writers never produce that layout (always axes="CYX"), so the branch is defensive — and correspondingly unexercised in production. The newer readers took the other answer to the same problem: tile_for_basic refuses a channel-last slide by name rather than carrying a second code path for an input its own upstream cannot emit.

bin/generate_preprocess_qc.py:180-205 · bin/split_multichannel.py:175-200 · bin/tile_for_basic.py:80-86 (refuses instead)
WAS “the one opportunity that is left” — convert_image.py's BioIO img.data  →  TAKEN
what it needed, and what it got

Not a tiled_io change: img is a bioio.BioImage, not a tifffile/zarr handle, so the fix had to come from BioIO's own API. The read is now img.dask_data at all three sites — the singleton-C squeeze, the S-as-C branch and the fallthrough. Every operation that follows (np.squeeze, np.transpose, np.take, plain indexing) dispatches through dask's __array_function__ and stays lazy, so none of the dimension-order logic had to be rewritten.

bin/convert_image.py:40 (read_image_bioio) · bin/utils/ome_io.py:428 (write_ome_tiff)
why the read alone would have saved nothing

Both halves had to change. A lazy handle passed to tifffile.imwrite is simply np.asarray'd — the materialisation moves from the read to the write and the peak is unchanged. The write now streams: TiffWriter.write(iterator, shape=, dtype=), the same form bin/tiled_stitch.py already used in production. Measured at 435 → 168 MB peak (panel d).

bin/utils/ome_io.py:321 (_iter_planes) · :313 (_axis0_slabs)
the near miss, and the risk that is left The obvious streaming iterator — one image_data[i] per plane — is a regression, not a win, when the reader hands back the whole stack as a single chunk: each plane's compute() re-decodes that chunk, so 8 planes cost 8 whole-stack decodes. The natural defence does not defend: .rechunk((1, Y, X)) splits the graph downstream of the source read and dask does not cache across independent computes, so it was measured at 9 decodes, unchanged, and rejected on that evidence rather than shipped because it looked right. What ships instead walks the array's own axis-0 chunk boundaries and materialises one slab: exactly one decode per chunk, for every chunking.

The residual risk is not ours to remove. Chunk granularity is the reader's decision — a bioio plugin that returns the slide as one chunk collapses the saving back to roughly the eager peak (384.8 MB against 167.7). That case is bounded, never worse than the write it replaced, and warned about by name at runtime — “the streamed write must decode them together … size this task from the DECOMPRESSED slide” — with a committed control test so the warning cannot decay into noise that always fires. And it is unobserved: bioio is not installable on the machine that measured any of this, so the real BioImage.dask_data was never called. That is the one claim in this figure resting on another library's documented behaviour rather than on something run.

The dials that govern this — and the ones that did not move

This work introduced no pipeline parameter; its only tunables are code constants. Its footprint on the scheduler is unchanged, which is the single most consequential fact for anyone hoping this made runs cheaper.

resource requests: unchanged at these five — three others were lowered

GENERATE_REGISTRATION_QC100 / 200 / 300 GB by (registered + reference).size()
GENERATE_PREPROCESS_QC100 GB + 100 GB × attempt via label 'process_medium'

Every one of the five above is a closure over file size, not over measured peak memory. A lower peak therefore changes nothing the scheduler reserves at those — the cluster still holds the same nodes for the same time. What a lower peak buys there is headroom: fewer OOM kills at the top of the size distribution.

Elsewhere the evidence did arrive, and three closures moved. This figure used to end with “no closure anywhere was lowered” and “the scheduler sees nothing”. Both are false, and the correction is the most consequential line in the panel — read verbatim from conf/modules.config:

MERGE_AND_PYRAMID300 GB → formula off a flat f<20 ? 200.GB : 300.GB ladder onto four terms with an 8 GB floor. Only one term carries the channel count, and the base term is 3.25 × the largest single channel file, deliberately not their sum — the O(C) shape the streaming rewrite removed.
APPLY_PROFILESdropped its × 7.GB term no file-size term at all now: the BASIC profile planes (2 × 16 × preproc_tile_size² × 8 bytes) plus write-tile buffers, floored at 8 GB. The old coefficient was applied to the compressed size and under-shot.
TILE_FOR_BASICcarries an explicit “NO FILE-SIZE TERM” O(preproc_tile_size²) buffers only, floored at 6 GB — legitimate only because CONVERT_IMAGE now writes tiled, so a region read decodes a tile rather than a whole plane.

All three are the same mechanism this figure documents, applied at write time as well as read time, and all three are guarded: a spy over the lazy view fails if the largest single materialisation grows with the channel count.

CONVERT_IMAGE is the sharpest case of that mismatch, and the reason the streamed write matters more than its megabytes suggest: the tier is read off the compressed file, while the peak was set by the decompressed one. A 6 GB CZI that decompresses to 20 GB is sized at 48 GB — and the eager write's own measurement put its peak at 2.4× the slide it was writing. The streamed write is what breaks that coupling — and the runtime warning of panel g says the same sentence out loud when the reader's chunking re-establishes it.

the split, which is a separate change PREPROCESS (4 cpus, 7 GB per GB of input + 8) became three processes when illumination correction was handed to nf-core's BASICPY: TILE_FOR_BASIC (2 cpus), BASICPY (1 cpu, 32 GB × attempt) and APPLY_PROFILES (2 cpus). That split is not a laziness result — one process became three and each needed its own request. What is a laziness result is that two of the three now carry no file-size term at all, which is the table above. This callout previously gave both of them per-GB coefficients (3 GB/GB + 8 and 7 GB/GB + 8) that neither has.
i

Three claims the original audit got wrong, and the one cause behind all three

The audit that scoped this work named three overread factors. All three were wrong, and wrong in the same way. This is the most transferable content in the figure: they are not arithmetic slips, they are a method failure.

CLAIMED “16× overread, twice” at registration QC
what is true

The channel overread was real, and is removed. The spatial overread was never overread: those full-resolution pixels are written to *_QC_RGB_fullres.tif, a published artifact. A “16× saving” would have been a silent downgrade of a deliverable.

what the read site could not tell you

What the pixels are for. That is decided at a write site tens of lines further down, and in conf/modules.config's publishDir.

CLAIMED “up to 100× overread” at preprocess QC
what is true

No I/O saving is available at all. The consumer is an anti-aliased resize, which needs every source pixel by definition. The real — and measured — win at this site is peak memory, a different quantity that the audit did not name.

what the read site could not tell you

Which filter consumes them. The disqualifying property lives inside skimage.transform.resize's anti_aliasing=True, one call further on.

CLAIMED the hot path is convert_image.py:167
what is true

Wrong site. That line is read_single_ndpi, blocked for an unrelated reason (panel g, blocker 3). The path the plan actually measured is img.data in read_image_bioio — and it belongs to BioIO, so tiled_io could never have fixed it. It was fixed through BioIO's own API instead, later and separately (panel g).

what the read site could not tell you

Which library owns the read. Two eager reads in one file, in different libraries, with different fixes and different feasibility.

the common cause All three came from scanning read sites. A read site tells you that bytes are fetched. It cannot tell you what the pixels are for (a published artifact), what filter consumes them (anti-aliasing), which library owns the read (BioIO), or how coarsely that library chunks what it hands back — the last of which is worth a number, because it was measured after the fact: the identical img.dask_data expression peaks at 167.7 MB when the reader chunks per plane and 384.8 MB when it returns one chunk, and nothing at the read site distinguishes the two. In every one of these cases the decision that governs the optimisation was made somewhere else — at a write site, inside a filter, in another library, or in that library's chunking policy. An overread factor read off a read site is a hypothesis, not a measurement.

Honest limits: what this figure does not claim

Everything a reader is entitled to hold against the work.

no production measurement

Nothing here was measured on a gigapixel slide, with a full marker panel, or inside a production container. Every number came from synthetic data on one laptop.

the harnesses are not committed

All three measurement scripts were scratch files outside the repository. No megabyte figure here can be reproduced from a checkout. The equivalence tests can, and so — for the convert alone — can the decode-count that the peak depends on.

the BioIO peak used a stand-in

bioio is not installable on the machine that measured it, so the 435 → 168 MB run used a tifffile-zarr-backed dask array, not the real BioImage.dask_data. The one thing that governs the saving — that reader's chunk granularity — is therefore unobserved.

no bytes-read reduction is claimed

Four of the five sites read exactly as many source pixels as before, and so does the convert. Only SEGMENT genuinely decodes less, and only on the channel axis.

the scheduler sees less, but only at three processes

This box used to read “the scheduler sees nothing — no run got cheaper in reserved GB·h, and no closure was lowered”. Panel h now quotes that sentence by name as false. Three closures were lowered: MERGE_AND_PYRAMID off a flat 300 GB reservation, APPLY_PROFILES minus its × 7.GB term, TILE_FOR_BASIC onto an explicit “NO FILE-SIZE TERM”. The two latter now request no function of input file size at all, so the first half of the old sentence was independently false as well. The limit that survives is narrower: at the five processes listed in panel h the request is still a closure over file size, so a lower peak there buys headroom rather than cost.

the channel-last branches stay untested in production

Every eager fallback is covered by unit tests on synthetic channel-last inputs, and by nothing else, because this pipeline never writes that layout.

what a green suite does and does not prove here The Python suite went from 711 to 812 passed / 9 skipped, and the stub run still publishes the same set of files it did before. That count was 62 when this work landed; re-measured 2026-09-01 on Nextflow 26.04.6 the same full-publish run gives 64 — the two files added since are P001_registrar.pickle and qc/preflight_scale_report.json, and nothing was lost. Until 2026-09-06 which number you got depended on how the cleanup level reached the publish gates, because they were plain booleans evaluated when conf/modules.config was parsed, before any profile or -c file had been applied: 64 with --cleanup_level none on the command line or in a -params-file, 29 with --cleanup_level final, and 32 for a bare -profile test, whose pinned level never reached them. The gates are now saveAs: closures resolved per file at publish time, so every route gives 64 at none and tests/cleanup_level_pin.sh holds it there. That establishes the equivalence claims — byte-identical outputs and no whole-stack decode — SPLIT_CHANNELS on raw file bytes, registration QC and preprocess QC on np.array_equal, the convert on full file bytes with the OME UUID masked, and both BASICPY-path readers on the size of every array their lazy view hands back. It establishes none of the megabyte figures: no test in this repository measures peak RSS. A test can see that a whole stack was not materialised; it cannot see what the process's resident set peaked at.

Supplementary Figure S4. Lazy reads: a peak-memory transition and its boundaries. (a) Lazy zarr-backed region reads were not added by this work — they had existed in bin/utils/tiled_io.py and were consumed by three STARE tiled scripts; what changed is reach. Two axes of overread exist, and only the channel axis was ever removable here. (b) The primitive: a channel-first lazy view, a byte-budgeted band reader, and one shared decimation factor. (c) Four sites changed, each stated at the confidence it earned — registration QC on pixel-identical output and SPLIT_CHANNELS on byte-identical files, both with a structural memory argument; preprocess QC and both segmentation backends on direct measurement. A fifth site, PREPROCESS, no longer exists: the in-process BaSiC correction was replaced by nf-core's BASICPY. It was the only card carrying no measurement, and the property survived the process — the two mirage-owned steps that replaced it read one channel at a time by construction, asserted on materialised bytes. (d) The three measurements, with their method and the scratch-only provenance that makes every megabyte figure irreproducible from the repository; the load-bearing results are the scaling shape — doubling the channel count grew the old peak 31% and the new one 1.3% — and the convert's 435 → 168 MB. (e) The comment both segmentation backends carried was false: asarray(out="memmap") decodes the entire compressed image into a new full-size uncompressed temporary file and maps that instead of the source. (f) Fourteen processes are untouched, in three classes — whole-array algorithms whose objects cross block boundaries, consumers whose input is already one plane or is a table, and reads owned by another library (VALIS, and now the vendored nf-core BASICPY container) — while the STARE per-tile path shows the ceiling a window-bounded design reaches, as opposed to a swapped read call; TILED_COARSE is the exception, at ~31.7 GB against a 48 GB request since its anchor became a U-Net. (g) Four mechanisms block a spatial saving even where the read is now lazy, and the opportunity this figure once listed as the only one left (convert_image.py's BioIO img.data) has been taken, through that library's own API: lazy read plus streamed chunk-slab write, with the naive per-plane iterator measured to be a regression and .rechunk() measured not to defend against it. (h) No parameter was added, and five of the affected processes still reserve memory as a function of input file size — the convert from the compressed input, while its peak was set by the decompressed one — so at those five a lower peak buys headroom, not cost. At three it bought cost: MERGE_AND_PYRAMID came off a 300 GB reservation, APPLY_PROFILES dropped its × 7.GB term, and TILE_FOR_BASIC now carries an explicit “NO FILE-SIZE TERM”. This panel asserted the opposite until 2026-08-30. (i) Three claims in the audit that scoped this work were wrong, all for one reason — a read site cannot tell you what the pixels are for, what filter consumes them, which library owns the read, or how coarsely that library chunks it.
