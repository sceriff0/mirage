# What the registration benchmark ADDS to upstream's VALIS 1.2.0 image
# (cdgatenbee/valis-wsi:1.2.0, the base of containers/valis120/Dockerfile ->
# bolt3x/mirage-valis120; benchmarks/regbench, method `valis`, labels `valis120` and
# `valis120_hires`). No pipeline process runs in that image.
#
# VALIS ITSELF IS NOT IN THIS FILE. VALIS 1.2.0, torch, Kornia, pyvips, libvips, the JVM
# and Bio-Formats are the ones upstream built into its image (ruling R3.9b, 2026-10-10);
# containers/valis120/Dockerfile's header lists them and says how they were read. This
# file holds only what the benchmark's own code needs beside them:
#   - What STARE's reader needs. Every method's images are read through stare.slide_io
#     (tifffile's zarr view), so the pinned stare-registration is installed in every
#     method image; it needs zarr 2, numcodecs and imagecodecs, which upstream's image
#     lacks.
#   - pytest: the first command on the cluster runs the benchmark's tests in the image.
#   - psutil is NOT here: upstream's image already has it (7.0.0).
#
# WHAT THE BENCHMARK ADDS IS HARMONISED; WHAT UPSTREAM BUILT IS LEFT ALONE. The lines
# below are the versions of requirements/constraints.txt, which this file reads like the
# other images' files. Nothing below depends on scipy, scikit-image or pandas, so the
# harmonised pins of those (scipy 1.15.3 against upstream's 1.16.0, pandas 2.3.3 against
# 2.3.0) never enter the resolve. The Dockerfile adds a second constraint, the freeze of
# the base image, so pip can add these lines and cannot move anything else.
#
# NOT `-r stare.txt`, AND STARE ITSELF IS NOT IN THIS FILE. stare.txt names numpy, scipy
# and scikit-image at the harmonised versions and would replace upstream's scipy. STARE's
# own requirements (stare-registration 1.2.1, pyproject.toml [FULL]: numpy>=1.26,
# scipy>=1.13, scikit-image>=0.24, tifffile<=2025.5.10, zarr>=2.18,<3, numcodecs<0.14,
# imagecodecs>=2023) are all met by upstream's stack plus the lines below, but resolving
# them would bring scipy and scikit-image under the harmonised constraint. The Dockerfile
# therefore installs STARE's one pinned line (cut out of requirements/stare.txt, so the
# version is still written once) with --no-deps, as containers/palom does, and smoke.sh
# checks every one of STARE's requirements against what is installed.
#
# THE ONE VERSION OF UPSTREAM'S STACK THAT IS CHANGED: tifffile. Upstream's image has
# tifffile 2025.6.11, and STARE requires tifffile<=2025.5.10: releases after that refuse
# zarr 2 in `aszarr` ("zarr 2.18.7 < 3 is not supported"; stare-registration 1.2.1,
# pyproject.toml [FULL], measured by STARE's authors on Python 3.12, which is this image's
# Python). Without the downgrade the benchmark could not read a single image here. VALIS
# 1.2.0 imports tifffile nowhere (its PyPI sdist [PARTIAL: every valis/*.py searched for
# the name]) and does not list it as a requirement (its pyproject.toml, read from the
# image's own layer [FULL]); it is in the image as a dependency of scikit-image, which
# accepts any tifffile>=2022.8.12. smoke.sh proves that this is the only line of
# upstream's freeze that differs.
-c constraints.txt

tifffile==2025.5.10     # replaces upstream's 2025.6.11, for stare.slide_io (above)
zarr==2.18.3            # stare.slide_io's lazy region reads
numcodecs==0.13.1       # zarr 2.18 imports blosc.cbuffer_sizes, gone from newer releases
imagecodecs==2025.3.30  # the codecs tifffile decodes the cohort's tiles with
pytest==9.1.1           # test_external_methods.py is run INSIDE the image first

# Everything else the resolver adds for the five lines above, pinned so a rebuild cannot
# move it. Checked on PyPI's JSON API on 2026-10-11: each release exists and has a wheel
# CPython 3.12 installs (asciitree is a source-only pure-Python release; pip builds it).
# packaging, which pytest also needs, is upstream's own (25.0) and stays.
asciitree==0.3.3        # zarr
fasteners==0.20         # zarr
iniconfig==2.3.1        # pytest
pluggy==1.6.0           # pytest
pygments==2.21.0        # pytest
